\sec User documentation

State-space is a~Clojure library for lazily exploring graphs and generated
state spaces. Graph searches yield visits lazily: maps whose \code{:state}
field contains a~value from the problem domain, with optional information
about how that state was reached.

To try the examples from the project directory, start a~REPL with
\code{clojure -M}; the source directory is on the classpath. Load the library
with:

\begtt \hisyntax{clojure}
(require '[state-space.core :as ss])
\endtt

The algorithm sections introduce the core searches in order. The later
sections on \ref[identity]{visit identity},
\ref[transitions]{additional visit data}, and
\ref[options]{termination} are reference material. All public operations
and options are explained here; the companion
\ulink[https://github.com/cao-/state-space/releases/latest/download/worked-examples.pdf]
{Worked examples PDF} provides practice rather than required background.
Evaluate this guide's snippets in order in one REPL session.

\secc Choosing an algorithm

Choose the operation by the result you need:

\begitems
* Use \code{dfs} to explore a~space depth-first when route length does not
  need to be minimized.
* Use \code{bfs} to find states in the fewest transitions when every
  transition has equal cost.
* Use \code{simple-paths} to enumerate cycle-free routes, keeping distinct
  routes that reach the same state. The number of routes can grow quickly.
* Use \code{postorder} to process each state after its successors, for example
  to order prerequisites or compute values bottom-up. On a~finite graph,
  cycles do not prevent traversal from finishing, but the result is not
  a~topological order.
* Use \code{best-first} to prioritize visits by cumulative non-negative cost
  (Dijkstra's algorithm by default), or by a~custom priority when that
  priority suits the problem.
* Use \code{propagate} when arrivals contribute information that must be
  joined and sent through the space again when it changes.
\enditems

Start with a~state and a~successor function. Put information that changes
future moves in the state itself: for example, \code{[location fuel]} when
remaining fuel determines which roads are usable. The default identity then
distinguishes those search positions without custom callbacks.
Add route context, such as a~path or distance, when it is needed; extensions
and custom visit keys are not prerequisites for using the library.

Search results are ordinary sequences: select goals with \code{filter} or
\code{some}, take a~prefix with \code{take}, or collect results with
\code{into}. A~fixed sequence of values or a~flat first-match lookup can
already be expressed with \code{reductions} or \code{some}; it does not
need a~search.

\secc Search spaces and depth-first search

A~state is a~value from the problem domain, such as a~location, puzzle board,
or configuration. A~{\it space} says which states can follow a~state. A~space
may be an adjacency map or a~function that returns successors for a~state.
DFS explores a~visit's successors before returning to pending siblings.
Starts and successors are considered in the order supplied. If a~space
returns an unordered collection, such as a~set or map, its iteration order
may vary; that can change which of several equally good routes is found
first. Use an ordered collection when a~particular tie-break is important.

An adjacency map can be passed directly as the space:

\begtt \hisyntax{clojure}
(def graph
  {:start [:left :right]
   :left  [:goal]
   :right [:goal]
   :goal  []})

(ss/dfs graph [:start])
;; => ({:state :start} {:state :left}
;;     {:state :goal} {:state :right})
\endtt

The common call shape is \code{(ss/dfs space starts options)}, with the
options map optional. \code{starts} is a~collection of starting states, even
when there is only one. To start at a~vector-valued state such as
\code{[0 0]}, pass \code{[[0 0]]}. The other graph searches use the same
call shape; propagation takes a~map of initial state values instead.

The first route reaches \code{:goal} through \code{:left}, so the default
behavior reports that state once and does not report its later arrival
through \code{:right}. A~missing map entry is also fine: it has no
successors and is treated as a~leaf.

A~space can be a~function instead of a~stored graph. By default, it receives
the current \code{:state} and returns a~collection of successor states:

\begtt \hisyntax{clojure}
(defn successors [n]
  (when (< n 3)
    [(inc n)]))

(mapv :state (ss/dfs successors [0]))
;; => [0 1 2 3]
\endtt

DFS is lazy: it does not construct the whole state space before returning
visits. The consumer can take a~finite prefix even when the space is infinite:

\begtt \hisyntax{clojure}
(mapv :state
      (take 4 (ss/dfs (fn [n] [(inc n)]) [0])))
;; => [0 1 2 3]
\endtt

Successors of a~yielded visit are requested only when the consumer asks for
more results.

\secc[context] Visits and route context

The simplest visit contains just \code{:state}. When a~search needs to keep
track of how it reached a~state, extensions add context fields such as
\code{:depth} or \code{:path}. Pass the built-in depth extension in the
options map to include the number of transitions from the start:

\begtt \hisyntax{clojure}
(ss/dfs graph [:start]
        {:extensions [ss/depth-extension]})
;; => ({:state :start :depth 0} {:state :left :depth 1}
;;     {:state :goal :depth 2} {:state :right :depth 1})
\endtt

The path extension records the states on the route so far. Extensions can
be combined in the same search:

\begtt \hisyntax{clojure}
(take 2 (ss/dfs graph [:start]
                {:extensions [ss/depth-extension
                              ss/path-extension]}))
;; => ({:state :start :depth 0 :path [:start]}
;;     {:state :left :depth 1 :path [:start :left]})
\endtt

An extension is a~map of callbacks, not data copied into each visit. For
example, the depth extension is equivalent to:

\begtt \hisyntax{clojure}
{:start (fn [_visit] {:depth 0})
 :next  (fn [parent _transition _visit]
          {:depth (inc (:depth parent))})}
\endtt

\code{:start} receives a~starting visit, initially \code{\{:state start\}},
and returns fields to merge into it. \code{:next} receives the parent visit,
the transition to the child, and the child visit being built; it returns
fields to merge into the child.
Without edge decoding, the transition is simply \code{\{:state child-state\}}.
Callbacks may be omitted when no work is needed at that stage.

Extensions run in order. Each callback sees the visit fields added by
earlier extensions at that stage, and later results override same-named
context fields. Callbacks must preserve \code{:state}; use separate keys
for context, preferably namespaced keywords in independently reusable
extensions to avoid accidental collisions. Post-order traversal reserves
\code{:value} for computed fold results, and \code{:via} and
\code{:back-edge} for successor views;
extensions must not use these as their own context fields.
These are caller expectations, not runtime checks; inputs that violate them
may produce unexpected results.
Section~\ref[transitions]{Additional visit and transition
data} shows a~custom extension using all these inputs.

\secc Breadth-first search

BFS visits all states at one edge-count depth before visiting states at the
next depth. It is useful when the goal is a~state nearest to any of the
starting states in an unweighted space. For example, DFS follows the detour
first in this graph, while BFS finds the nearer route:

\begtt \hisyntax{clojure}
(def routes {:start [:detour :near]
             :detour [:middle]
             :middle [:goal]
             :near [:goal]
             :goal []})

(ss/bfs routes [:start])
;; => ({:state :start} {:state :detour} {:state :near}
;;     {:state :middle} {:state :goal})
\endtt

By default, BFS reports each state only on its first arrival. In a~static
space, this means it reports a~state at its minimum edge-count depth from any
start; here the first route to \code{:goal} is the two-edge route through
\code{:near}. See section~\ref[identity]{Visit identity} for how to change
which arrivals count as distinct.
If multiple routes reach a~state at that depth, start order and successor
order determine which route is retained. BFS does not account for edge
weights; use it when every transition has equal cost.

The basic search needs no extensions; each visit contains its state. Add the
depth extension when the edge-count depth is useful:

\begtt \hisyntax{clojure}
(ss/bfs routes [:start]
        {:extensions [ss/depth-extension]})
;; => ({:state :start :depth 0} {:state :detour :depth 1}
;;     {:state :near :depth 1} {:state :middle :depth 2}
;;     {:state :goal :depth 2})
\endtt

To retrieve the shortest route, add the path extension and select the first
goal visit. The remaining search is not expanded:

\begtt \hisyntax{clojure}
(->> (ss/bfs routes [:start]
                 {:extensions [ss/path-extension]})
     (filter #(= :goal (:state %)))
     first
     :path)
;; => [:start :near :goal]
\endtt

If no goal is reachable and the search finishes, \code{first} returns
\code{nil}. It cannot report failure if the remaining search runs forever.

All starting visits are at depth zero and are visited before any successors.
BFS is lazy too. A~bounded prefix can be consumed even from an infinite
space:

\begtt \hisyntax{clojure}
(mapv :state
      (take 4 (ss/bfs (fn [n] [(inc n)]) [0])))
;; => [0 1 2 3]
\endtt

\secc Simple paths

\code{simple-paths} enumerates routes depth-first without revisiting a~state
within a~route (by default). Unlike DFS, it does not discard a~state merely
because a~different route reached it first. This is useful when all
cycle-free ways through a~small graph matter. Like the other searches, it
first returns visits with just their \code{:state}. Here the repeated
\code{:c} is reached by two distinct routes:

\begtt \hisyntax{clojure}
(def paths {:a [:b :c]
            :b [:c]
            :c [:a]})

(ss/simple-paths paths [:a])
;; => ({:state :a} {:state :b} {:state :c} {:state :c})
\endtt

To see each route prefix explicitly, add the path extension:

\begtt \hisyntax{clojure}
(mapv :path
      (ss/simple-paths paths [:a]
                           {:extensions [ss/path-extension]}))
;; => [[:a] [:a :b] [:a :b :c] [:a :c]]
\endtt

The default path identity is \code{:state}; \code{:visit-key} can select a~
different identity (see section~\ref[identity]{Visit identity}), and
\code{:visit-key nil} disables the per-route repetition check. Simple-path
results are lazy; for example, a~bounded prefix of an infinite chain can be
consumed:

\begtt \hisyntax{clojure}
(mapv :state
      (take 4 (ss/simple-paths (fn [n] [(inc n)]) [0])))
;; => [0 1 2 3]
\endtt

A~finite graph can still have many simple paths.

\secc Post-order traversal

\code{postorder} returns each state after its successors, in depth-first
post-order. When edges point from a~task to its prerequisites, prerequisites
therefore appear first. For example, this gives a~valid build order:

\begtt \hisyntax{clojure}
(ss/postorder {:package [:compile]
                     :compile [:parse]
                     :parse []}
                    [:package])
;; => ({:state :parse} {:state :compile} {:state :package})
\endtt

On a~cyclic graph, back edges are ignored for traversal and the search
terminates with DFS post-order when the reachable graph and its successor
collections are finite; that order is a~valid topological ordering only when
the reachable graph is acyclic.
Post-order traversal requires a~non-\code{nil} \code{:visit-key}.

Post-order traversal is lazy between completed visits, but it finishes
processing a~visit's successors before returning that visit. Taking the first
result does not require enumerating every successor. Here, the root has
infinitely many leaf successors, but the first completed visit is available
immediately:

\begtt \hisyntax{clojure}
(defn dependencies [task]
  (if (= task :root)
    (map #(vector :task %) (range))
    []))

(mapv :state (take 1 (ss/postorder dependencies [:root])))
;; => [[:task 0]]
\endtt

The library decodes transitions and runs extension callbacks one at a~time.
A~chunked lazy successor collection returned by the space may itself compute
several raw successors when its first item is requested.

Post-order traversal also supports a~streaming \code{:fold} over completed
successors, with \code{reduced} for early stopping. Its examples
appear in section~\ref[transitions]{Additional visit and transition data}.

\secc[propagation] State propagation

\code{propagate} is a~different kind of graph computation: instead of
discarding later arrivals at a~state, it joins their information and
processes that state again when the joined value changes. This is useful for
analyses that circulate information through cycles, such as reaching
definitions in a~compiler control-flow graph.

\code{propagate} takes a~space, a~map from starting states to initial
values, and an options map. \code{:join} combines a~state's old value with
an incoming contribution. \code{:bottom} is the value used before a~state
has received any contributions; it should be an identity for the join.
For sets of known facts, these are set union and the empty set:

\begtt \hisyntax{clojure}
(require '[clojure.set :as set])

(def tiny-space {:start [:next]
                 :next []})

(:values (last (ss/propagate tiny-space
                                 {:start #{:ready}}
                                 {:bottom #{}
                                  :join set/union})))
;; => {:start #{:ready}, :next #{:ready}}
\endtt

The result is a~lazy sequence of progress records, not a~sequence of visits:

\begtt \hisyntax{clojure}
(ss/propagate tiny-space {:start #{:ready}}
              {:bottom #{} :join set/union})
;; => ({:values {:start #{:ready}} :changes []}
;;     {:values {:start #{:ready} :next #{:ready}}
;;      :processed :start
;;      :changes [{:state :next :value #{:ready}}]}
;;     {:values {:start #{:ready} :next #{:ready}}
;;      :processed :next :changes []})
\endtt

The initial record has no \code{:processed} key because no state has been
processed. Later records contain the state just processed, the resulting
\code{:values} map, and a~vector of destination updates in \code{:changes}.
Updates follow transition order. A~destination can appear more than once,
with its accumulated value after each update; \code{:values} holds the
values after all transitions for that record. Contributions that leave a~
known value unchanged add no entry, but a~newly discovered state is recorded
even at \code{:bottom}. Use \code{last} only when propagation terminates.

By default the space receives just the state and sends its current value
unchanged to every successor. To transform that information, pass
\code{:project identity}: the space then receives
\code{\{:state state :value value\}}. Use \code{:decode-edge identity} when
its successors are already transition maps; each transition contains a~
destination \code{:state} and an optional \code{:value} contribution.
If \code{:value} is absent, the current value is passed on unchanged.
Here each state adds its own fact before contributing to its neighbour:

\begtt \hisyntax{clojure}
(defn share-facts [{:keys [state value]}]
  [{:state ({:a :b :b :a} state)
    :value (conj value state)}])

(:values (last (ss/propagate share-facts {:a #{}}
                            {:project identity
                             :decode-edge identity
                             :bottom #{}
                             :join set/union})))
;; => {:a #{:a :b} :b #{:a :b}}
\endtt

Both states are processed again as their sets grow. Once sending
information around the cycle changes neither set, the worklist empties.
State map keys are identities, not visit keys; they may be any Clojure
value, including \code{nil} and \code{false}. Propagation does not use
extensions.

Unlike the search algorithms, propagation intentionally revisits a~state
when its value changes. For order-independent results, the join should be
associative, commutative, and idempotent, and transfer functions should be
monotone in the information order: learning more at a~state must not
invalidate facts it previously sent. Termination depends on the problem:
the two facts above can only accumulate to a~fixed point, but arbitrary
spaces and value domains need not stabilize. These are
caller assumptions; the library does not validate them. Each expanded state
must return a~finite successor collection. Ordinary shortest-path costs do
not need this operation; the next section covers
\ref[best-first]{best-first search}.

\secc[best-first] Best-first search

\code{best-first} chooses the pending visit with the lowest priority.
By default its \code{:distance} is the sum of transition weights, with each
edge costing one unless \code{:decode-edge} supplies a~\code{:weight}. It is therefore
\ulink[https://en.wikipedia.org/wiki/Dijkstra's_algorithm]{Dijkstra's search}
when weights are finite and non-negative:

\begtt \hisyntax{clojure}
(def routes {:home [:slow :quick]
             :slow [:goal]
             :quick [:goal]
             :goal []})

(ss/best-first routes [:home])
;; => ({:state :home :distance 0} {:state :slow :distance 1}
;;     {:state :quick :distance 1} {:state :goal :distance 2})
\endtt

To account for different transition costs, supply \code{:decode-edge},
a~function that converts each raw successor into a~transition map.
The map's required \code{:state} identifies the destination; other fields
describe the edge. The built-in distance extension reads \code{:weight},
defaulting to one when that field is absent:

\begtt \hisyntax{clojure}
(def weighted-routes
  {:home [[:slow 5] [:quick 1]]
   :quick [[:goal 2]]
   :slow [[:goal 1]]
   :goal []})

(ss/best-first weighted-routes [:home]
               {:decode-edge (fn [[state weight]]
                               {:state state :weight weight})})
;; => ({:state :home :distance 0} {:state :quick :distance 1}
;;     {:state :goal :distance 3} {:state :slow :distance 5})
\endtt

An optional \code{:priority} function can order visits by something other than
distance, or add an estimate of the remaining cost as in
\ulink[https://en.wikipedia.org/wiki/A*_search_algorithm]{A* search}. A custom
priority does not automatically calculate \code{:distance}; include
\code{ss/distance-extension} explicitly when the priority or results need
it. For example, a~route planner can combine the cost already travelled with
a~lower-bound estimate to the goal:

\begtt \hisyntax{clojure}
(def roads {:home [[:hill 1] [:river 2]]
            :hill [[:goal 5]]
            :river [[:goal 2]]
            :goal []})
(def estimate {:home 3 :hill 4 :river 2 :goal 0})

(->> (ss/best-first roads [:home]
                        {:decode-edge (fn [[state weight]]
                                        {:state state :weight weight})
                         :extensions [ss/path-extension
                                      ss/distance-extension]
                         :priority (fn [{:keys [state distance]}]
                                     (+ distance (estimate state)))})
     (filter #(= :goal (:state %)))
     first
     :path)
;; => [:home :river :goal]
\endtt

With the default \code{:visit-key} of \code{:state}, best-first settles each
state key at most once, using the best priority offered for it before
settlement. For A*, a~consistent heuristic with value zero at the goal is
sufficient for an optimal first goal: for every edge from \code{u} to
\code{v}, its estimate must satisfy \code{h(u) <= weight(u,v) + h(v)}.
An admissible heuristic never overestimates the remaining cost.
An admissible but inconsistent heuristic may
need a~state to be explored again after a~better route is found. When the
heuristic depends only on the state, use a~\code{:visit-key} that distinguishes
different path costs, for example \code{(juxt :state :distance)}; this lets
best-first treat each state and cost pair as a~separate search position.
This may greatly increase the search and may prevent termination on cyclic
spaces. It is not a~general reopening mechanism for priorities that depend on
other visit context. Transition weights must be finite and non-negative.
Equal priorities are emitted in FIFO enqueue order; when starts or
successors come from an unordered collection, their tie order may vary.
Zero-weight edges are supported, but on an infinite space an infinite region
of equal or lower priority can indefinitely delay a~positive-cost result.
The usual A* completeness and optimality guarantees assume bounded branching,
an admissible heuristic, and edge costs bounded below by a~positive value;
with multiple-path pruning, consistency is also needed for the usual
optimality guarantee.
Best-first requires a~finite collection of starting states and finite
successor collections for each expanded visit. The default distance priority
automatically includes \code{distance-extension}; custom priorities do not.

Best-first is lazy as well. Starting states are consumed and initialized
only when the result is consumed; all starts are queued before selecting
the first visit. With the default distance priority, visits are emitted in
nondecreasing cost order. A~finite prefix can be consumed even when the
search space is infinite:

\begtt \hisyntax{clojure}
(mapv :state
      (take 4 (ss/best-first (fn [n] [(inc n)]) [0])))
;; => [0 1 2 3]
\endtt

\secc[identity] Visit identity

By default, DFS, BFS, post-order traversal, and best-first treat visits with
equal \code{:state} values as the same search position. This avoids exploring a~
state repeatedly and, for cyclic graphs, prevents traversal from following
cycles forever. More precisely, the visit key determines which arrivals an
algorithm treats as duplicates; later visits with a~key already seen are
skipped rather than combined with the earlier visit. The exact first arrival
depends on the search: DFS order for DFS, minimum edge-count depth for BFS in
a~static space, and minimum accumulated path cost for best-first with its
default distance priority and non-negative weights.

Sometimes context matters: the same state reached at different depths may
need to be explored twice. Choose a~\code{:visit-key} that includes that
context:

\begtt \hisyntax{clojure}
(def context-routes {:start [:near :detour]
                     :near [:goal]
                     :detour [:middle]
                     :middle [:goal]
                     :goal []})

(ss/dfs context-routes [:start]
        {:extensions [ss/depth-extension]
         :visit-key (juxt :state :depth)})
;; => ({:state :start :depth 0} {:state :near :depth 1}
;;     {:state :goal :depth 2} {:state :detour :depth 1}
;;     {:state :middle :depth 2} {:state :goal :depth 3})
\endtt

Sometimes context should affect which successors are allowed, while each
state should still be expanded only once. For example, explore links up to
two steps from the start, expanding each location at its shallowest arrival.
BFS reaches a~state at minimum depth, and the default \code{:visit-key}
discards later arrivals to that state. The \code{:expand?} predicate receives
the full visit and decides whether to request successors; a~visit rejected
by it is still returned:

\begtt \hisyntax{clojure}
(def depth-limited-routes
  {:start [:junction :detour]
   :detour [:junction]
   :junction [:goal]
   :goal [:finish]
   :finish []})

(ss/bfs depth-limited-routes [:start]
        {:expand? #(< (:depth %) 2)
         :extensions [ss/depth-extension]})
;; => ({:state :start :depth 0} {:state :junction :depth 1}
;;     {:state :detour :depth 1} {:state :goal :depth 2})
\endtt

The second arrival at \code{:junction}, at depth two, is not returned or
expanded; the earlier arrival already expanded it with more steps remaining.
This is appropriate when the shallowest arrival is the one that should
govern exploration. If a~later arrival's context must also be explored, add
that context to \code{:visit-key}, as above.

The key function receives the full visit map. For DFS and BFS,
\code{:visit-key nil} disables global deduplication; on a~cycle, this can
produce an infinite result. \code{simple-paths} uses its key only to prevent
repeats within a~route; setting it to \code{nil} disables that check.
Identity affects correctness too: if equal keys can have different
successors, treating those visits as the same can change the search results.

For a~tree, disabling deduplication makes DFS visit each occurrence, like
\code{clojure.core/tree-seq}. The successor function supplies the children
directly, combining the roles of \code{tree-seq}'s \code{branch?} and
\code{children} functions; DFS still returns visit maps rather than bare
nodes. Here the two equal branch subtrees are distinct occurrences:

\begtt \hisyntax{clojure}
(def repeated-branch {:value :branch
                      :children [{:value :leaf}]})
(def tree {:value :root
           :children [repeated-branch repeated-branch]})
(defn values [nodes] (mapv :value nodes))

(values (map :state (ss/dfs :children [tree])))
;; => [:root :branch :leaf]

(values (map :state (ss/dfs :children [tree] {:visit-key nil})))
;; => [:root :branch :leaf :branch :leaf]

(values (tree-seq (comp seq :children) :children tree))
;; => [:root :branch :leaf :branch :leaf]
\endtt

With the default key, the second equal branch is skipped. Setting the key to
\code{nil} preserves both occurrences, matching \code{tree-seq}'s traversal.

\secc[transitions] Additional visit and transition data

Once an algorithm and its order are chosen, extensions can carry
problem-specific information in visits. As in weighted best-first search,
\code{:decode-edge} turns raw successors into transition maps. This works
with any graph search, not only best-first; transition fields do not
automatically become visit fields.

The built-in \code{trail-extension} records decoded transitions along a~
route. Unlike \code{path-extension}, it retains edge fields such as labels
or weights:

\begtt \hisyntax{clojure}
(def weighted-graph
  {:start [[:next 7]]
   :next []})

(ss/dfs weighted-graph [:start]
        {:decode-edge (fn [[state weight]]
                        {:state state :weight weight})
         :extensions [ss/trail-extension]})
;; => ({:state :start :trail [{:state :start}]}
;;     {:state :next :trail [{:state :start}
;;                           {:state :next :weight 7}]})
\endtt

Without a~decoder, each raw successor is treated as a~state, even if it is
a~map. The trail starts with \code{\{:state start\}}; later entries are the
decoded transitions. DFS, BFS, and \code{simple-paths} do not interpret edge
weights; the seven above is retained but does not affect DFS order.

A~custom extension can use all the inputs to \code{:start} and
\code{:next}. Here the depth extension runs first, so the visit being built
already contains \code{:depth}. The next extension records where each leg
started, its label, and the child's state and depth:

\begtt \hisyntax{clojure}
(def leg-extension
  {:start (fn [visit]
            {:legs [{:to (:state visit) :depth (:depth visit)}]})
   :next (fn [parent transition visit]
           {:legs (conj (:legs parent)
                        {:from (:state parent)
                         :label (:label transition)
                         :to (:state visit)
                         :depth (:depth visit)})})})

(ss/dfs {:home [[:park :walk]] :park []} [:home]
        {:decode-edge (fn [[state label]]
                        {:state state :label label})
         :extensions [ss/depth-extension leg-extension]})
;; => ({:state :home :depth 0 :legs [{:to :home :depth 0}]}
;;     {:state :park :depth 1
;;      :legs [{:to :home :depth 0}
;;             {:from :home :label :walk :to :park :depth 1}]})
\endtt

The parent supplies the accumulated legs, the transition supplies the edge
label, and the child visit supplies fields computed by earlier extensions.
Reversing the extension order would make \code{:depth} unavailable to
\code{leg-extension} at that stage. Callbacks run while candidate visits
are prepared, before duplicate detection; they can run for an arrival that
is ultimately skipped, including a~repeated start or a~path repeat rejected
by \code{simple-paths}. Prefer pure callbacks rather than using them as
notifications of emitted visits; perform actions on returned visits while
consuming the result sequence instead.

For the common case of carrying a~single value, \code{accumulate} builds
the \code{:start}/\code{:next} callbacks for you.
\code{(ss/accumulate key init step)} calls \code{init} with the starting
visit and \code{step} with the parent's value at \code{key} and the decoded
transition. For example, track remaining fuel along a~route:

\begtt \hisyntax{clojure}
(def fuel-extension
  (ss/accumulate :fuel-left (constantly 10)
                     (fn [fuel transition]
                       (- fuel (:fuel-used transition)))))

(ss/dfs {:trailhead [[:ridge 3]]
         :ridge []}
        [:trailhead]
        {:decode-edge (fn [[state fuel-used]]
                        {:state state :fuel-used fuel-used})
         :extensions [fuel-extension]})
;; => ({:state :trailhead :fuel-left 10} {:state :ridge :fuel-left 7})
\endtt

By default, a~space function receives only the current state. Set
\code{:project identity} to give it the full visit, including extension
values. This is useful when legal moves depend on search context:

\begtt \hisyntax{clojure}
(defn bounded-successors [{:keys [state depth]}]
  (when (< depth 2)
    [(inc state)]))

(ss/dfs bounded-successors [0]
            {:project identity
             :extensions [ss/depth-extension]})
;; => ({:state 0 :depth 0} {:state 1 :depth 1} {:state 2 :depth 2})
\endtt

The \code{:expand?} option can prune a~visit without removing it from the
result. It receives the full visit; when it returns false, the space is not
called for that visit and no successors are generated:

\begtt \hisyntax{clojure}
(ss/dfs {0 [1] 1 [2] 2 [3] 3 []}
        [0]
        {:extensions [ss/depth-extension]
         :expand? #(< (:depth %) 2)})
;; => ({:state 0 :depth 0} {:state 1 :depth 1} {:state 2 :depth 2})
\endtt

Post-order traversal can fold successor results into a~computed
\code{:value}. Supply a~\code{:fold} map with \code{:init}, which receives
each newly entered visit, and \code{:step}, which receives the accumulator
and one successor view. For example, count the tasks in each dependency
subtree:

\begtt \hisyntax{clojure}
(def subtree-size
  {:init (constantly 1)
   :step (fn [size child] (+ size (:value child)))})

(ss/postorder {:app [:lib :config]
               :lib [:base]
               :base []
               :config []}
              [:app]
              {:fold subtree-size})
;; => ({:state :base :value 1} {:state :lib :value 2}
;;     {:state :config :value 1} {:state :app :value 4})
\endtt

The accumulator belongs to its parent; it is not merged into route context
or passed to the space or \code{:next}. Each child is evaluated once per
visit key and contributes once per incoming edge. Counting distinct
descendants therefore requires sets, not a~sum.
No child vector is collected automatically. To keep children, explicitly
accumulate a~vector; to compute a~scalar, retain only that scalar.
The result cache remains necessary for sharing.

An optional \code{:finish} function converts the final accumulator into
the visit's \code{:value}; it defaults to \code{identity}. It runs once per
completed key, including leaves and early stops. It can extract a~result
from a~larger working accumulator. Return a~map value when computing
several results together.

Return \code{(reduced accumulator)} from \code{:step} to finish this parent
without requesting another successor. Here a~cached result prevents
exploring the fallback build:

\begtt \hisyntax{clojure}
(def cache-or-build
  {:init (fn [{:keys [state]}] (when (= state :cached) state))
   :step (fn [selected child]
           (if-let [source (:value child)]
             (reduced source)
             selected))})

(ss/postorder {:root [:cached :build]
               :cached []
               :build []}
              [:root]
              {:fold cache-or-build})
;; => ({:state :cached, :value :cached}
;;     {:state :root, :value :cached})
\endtt

Returning \code{reduced} from \code{:init} also skips the first successor,
without calling the space, projection, or expansion predicate.
The wrapper is removed before \code{:finish}. Parent steps run when
consumption resumes after yielding a~child; stopping at that child need not
run its parent's step. Chunked input may realize extra raw successors, but
no further transition is decoded after an early stop.

Each successor view carries \code{:via}, the transition from this parent,
and \code{:back-edge}, true if it refers to a~visit still being explored.
Back edges have no computed \code{:value}. This lets a~fold inspect cycles
without following them again:

\begtt \hisyntax{clojure}
(def edge-report
  {:init (constantly [])
   :step (fn [edges {:keys [state via back-edge]}]
           (conj edges [state (:kind via) back-edge]))})

(ss/postorder {:a [[:b :depends-on]]
               :b [[:a :depends-on]]}
              [:a]
              {:decode-edge (fn [[state kind]]
                              {:state state :kind kind})
               :fold edge-report})
;; => ({:state :b :value [[:a :depends-on true]]}
;;     {:state :a :value [[:b :depends-on false]]})
\endtt

Post-order traversal reuses the first visit for each key, including its
computed \code{:value}, when another parent reaches it. The \code{:via}
field describes the edge from the current parent, even if a~different
parent first reached that state. Bottom-up computations on a~DAG can reuse
completed successor values this way. On a~cycle, a~back edge refers to an
unfinished visit, so a~fold must not assume every successor has
its computed fields. Use \ref[propagation]{propagation} instead when
information must circulate until it stabilizes. If a~result depends on its
route, choose a~visit key that distinguishes the relevant context rather
than reusing another route's result. This includes context used by
\code{:expand?} or the fold: a~result computed under one budget or
pruning window is not automatically valid under another. Equal keys must
identify interchangeable computations; a~later arrival does not recompute
the cached result.
The key must remain stable from entry through completion; do not base it
on the computed \code{:value}. The reserved \code{:via} and
\code{:back-edge} fields are supplied in successor views, not on emitted visits. These input
expectations are not checked at runtime.

For option defaults and termination behavior, see
section~\ref[options]{Options and termination}.

\secc[options] Options and termination

The following options are common to the graph searches. Best-first also
accepts \code{:priority}. Post-order traversal supports a~\code{:fold},
described in
\ref[transitions]{Additional visit and transition data}.

\begitems
* \code{:project} chooses what is passed to the space, applied to the full
  visit. It defaults to \code{:state}.
* \code{:expand?} decides whether to request successors for a~visit, applied
  to the full visit. It defaults to a~function that accepts every visit; a~
  rejected visit is still returned.
* \code{:decode-edge} optionally converts each raw successor to a~transition
  map containing \code{:state}. Without a~decoder, the raw successor is the
  state.
* \code{:extensions} is an ordered collection of maps, empty by default.
  \code{:start} and \code{:next} callbacks return maps of route-context fields
  to add or replace.
* \code{:visit-key} selects the key used for duplicate detection, applied to
  the full visit. It defaults to \code{:state}; its meaning and restrictions
  vary by algorithm.
  Post-order traversal and best-first require a~non-\code{nil} key.
* Best-first also accepts \code{:priority}, a~function of the visit that
  determines queue order. It defaults to \code{:distance}, which automatically
  enables \code{distance-extension}. A custom priority does not add
  \code{:distance}; add \code{ss/distance-extension} to \code{:extensions}
  if it needs cumulative distance. Priority values must be mutually comparable.
* Post-order traversal also accepts \code{:fold}, a~map with required
  \code{:init} and \code{:step} functions and optional \code{:finish}.
  Without a~fold it returns visits without a~computed \code{:value}.
\enditems

\code{simple-paths} uses \code{:visit-key} to prevent repeats on each route,
rather than to deduplicate the entire search.

\code{propagate} uses \code{:project}, \code{:expand?}, and
\code{:decode-edge}; \code{:bottom} and \code{:join} are required. Its map
keys identify states, so it does not use \code{:visit-key} or
\code{:extensions}.

To exhaust a~result sequence after finitely many visits, the start collection
and the reachable search must be finite, and calls to the space and callbacks
must return.
Disabling deduplication on a~cycle can make DFS or BFS produce visits forever.
Simple-path enumeration can still be large even on a~finite graph because
there may be many distinct routes.

For an infinite space, DFS can follow an infinite branch forever, preventing
later siblings or starts from being reached. BFS reaches every visit at
finite depth when the start collection is finite and each visit has finitely
many successors; an infinite successor collection can prevent deeper levels
from being reached.
Post-order traversal must finish a~visit's successors before yielding it.
Best-first requires finite starts and finite successor collections for each
expanded visit. DFS, BFS, simple-path enumeration, and best-first results are
lazy, so use a~bounded operation such as \code{take} or \code{first} with
\code{filter} when only part of a~result is needed. Post-order traversal is
lazy between completed visits, but a~parent is not returned until its
successors have been processed.
An infinite sequence of leaf successors can therefore produce completed
visits indefinitely, although its parent cannot finish unless pruned.

Laziness does not mean constant memory or exactly one callback per returned
visit. Deduplication retains seen keys, BFS retains a~pending frontier, and
post-order traversal retains known visits and their computed values.
Path and trail extensions retain route data. Keeping the head of a~result
sequence also retains the realized visits; keeping propagation's progress
records retains their persistent value-map snapshots. A~chunked successor
sequence may compute several raw values at once, and best-first and
propagation consume all successors of an expanded state before producing
the next result.

The space must be callable on the projected value and return \code{nil} or a~
collection of successors. \code{:project}, \code{:visit-key}, and
\code{:expand?} must be callable; \code{:visit-key} may be \code{nil} only
where allowed above. When supplied, \code{:decode-edge} must return a~map
containing \code{:state}. Extension callbacks must return maps. Visit keys
should have stable equality and hashing. These input contracts are not
exhaustively validated at runtime.

\secc Computational costs

With deduplication enabled, for a~finite reachable graph with $V$ visit keys
and $E$ examined transitions, DFS, BFS, and post-order traversal perform $O(V+E)$ graph
bookkeeping. This treats hash-based lookup as effectively constant and
excludes successor generation, state hashing, callback work, and output
construction. Best-first uses a~keyed sorted queue, giving
$O((V+E)\log V)$ queue work. Simple-path enumeration depends on the number
of route prefixes, which may be exponential. Propagation also depends on
how often a~state's value improves, not just on graph size.

Callbacks can change these bounds. A~fold that collects children and
rescans the whole vector on every step does quadratic work in a~node's degree.
Use a~\code{:fold} for incremental summaries and only collect children
explicitly when the computation needs them.
Large set unions and arbitrary-precision arithmetic still cost what their
domain operations require.

Identity matters as much as the traversal: include information that affects
future choices or results, but do not distinguish histories merely because
they provide different witnesses. For trees with unique states,
\code{:visit-key nil} avoids a~visited set in DFS and BFS.

The library supplies traversal order, graph identity, reusable context, and
stack-safe dependency evaluation; it does not remove their allocation
costs. A~flat cumulative sum or first-match lookup needs no graph machinery.
The worked examples include direct alternatives for such cases.

\secc Visits, transitions, and extensions

The algorithms exchange visit maps. \code{:state} is the problem's state;
extensions add derived values to the same map. A~raw successor is either
already a~state or is decoded into a~transition map. Its \code{:state}
becomes the child's state, while the remaining transition fields are passed
to \code{:next} callbacks. This gives path, depth, trail, and application
specific extensions one shared lifecycle.
Callback maps are reduced directly by key and value into the visit, in
extension order.

\secc Preparing a search

The \code{search-options} helper resolves shared graph-search defaults and
configures a~visit-preparation function once at the start of an algorithm.
A~default-decoded transition already has the base visit's exact shape and
is reused before applying extensions. Custom decoders supply only the
destination to a~new base visit; other edge fields are available to
extensions but do not become visit context automatically.
The space is called
with the projected visit, and \code{:expand?} can make a visit a leaf without
removing it from the results. Decoding then gives each raw successor a
uniform transition-map shape. The local \code{map-lazy} helper delays its
mapping function one item at a time when initializing starts.

\secc Lazy work and frontiers

The results of the searches are lazy, but laziness here does not promise that
exactly one callback or successor is processed for each requested result.
\code{map-lazy} invokes its mapping function one item at a time; it is used
where start visits are prepared. Other sequence
operations, such as \code{keep} in the shared traversal, can realize a chunk
when their input is chunked. The space itself also controls how its
successors are produced, so consuming one raw successor may realize several
values from a chunked input. Best-first has an additional requirement: it
must examine all successors of the expanded visit before it can choose the
next visit by priority.
Propagation updates are processed one state at a time, but all of that
state's successors are joined before its progress record is returned.
Its initial record does not require constructing the worklist; that is
deferred until the first processing record is requested.

DFS and BFS keep pending work in a frontier of lazy chunks. A stack takes the
newest chunk first; a queue takes the oldest. Both consume items from the
current chunk in order, so successors retain their order without first being
flattened into one collection.
Successor generation itself is delayed until the chunk is consumed.
In BFS, earlier chunks can therefore supply visits without expanding those
visits or requesting work from later chunks.

\secc Shared traversal: DFS, BFS, and simple paths

\code{explore} owns the mechanics common to depth-first and breadth-first
search: pop a visit, optionally deduplicate it, yield it, then lazily prepare
its children and push them onto the frontier. Supplying a stack or queue
changes the order without duplicating this traversal logic. \code{simple-paths}
uses the same depth-first engine but replaces global deduplication with a
per-route refinement. The route's identity keys live in metadata, so they
control pruning without becoming part of the public visit.

\secc Post-order traversal

Post-order traversal cannot use the shared loop: a visit must be returned
only after its successors have finished. Its explicit pending items represent
entering a visit and resuming its parent. Compact vector frames store the
operation, visit, identity key, accumulator, remaining successors, and
optional awaited edge. An inner loop handles cached successors without
allocating frames for them. Lazy boundaries are needed when yielding
completed visits and descending into new children, not on every edge.
Pending frames form a sequence stack, with lazily initialized starts at
its tail. No chunk frontier is needed.
\code{known} stores the first visit for each key and replaces it at
completion. With a~fold, the reserved \code{:value} field distinguishes a~
completed result from an active visit, including results of \code{nil} or
\code{false}; no separate completion set is needed.
When a child finishes, its parent's fold step incorporates the completed
successor view into a~private accumulator. There is no implicit
processed-child collection.
The same state-only transition reuse applies here. Attributed transitions
keep their edge fields in \code{:via}, not in the visit itself.
A~\code{reduced} accumulator stops traversal before requesting another
transition; \code{:finish} receives its unwrapped value.
A~chunked source may nevertheless realize multiple raw successors as one
is consumed. If initialization returns \code{reduced}, the space and
expansion callbacks are not called for that visit.
Remaining successors are stored raw and decoded directly by the loop
after the pruning check, without an intermediate mapped sequence.

\secc Best-first traversal

Best-first orders pending visits by priority, so it uses a sorted map rather
than the DFS/BFS frontier. \code{queued} records the queue position for
each pending visit key; a better route replaces its previous queue entry,
so only one candidate per key remains pending. \code{settled} ensures each key
is emitted once. A monotonically increasing sequence number makes equal
priorities stable in insertion order. The default cumulative-distance
priority has Dijkstra's shortest-path behavior when edge weights are
non-negative.

\secc State propagation

Propagation uses the same projected visits and decoded transitions as the
searches, but its worklist is organized around accumulated values per state.
A state is requeued when joining a contribution changes its value; pending
states are coalesced so a state already waiting in the FIFO queue is not
queued twice. Each progress record contains a persistent snapshot of the value
map, the processed state, and its changed destinations. The initial snapshot
is yielded before any state is expanded.
